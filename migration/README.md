# Watchman v2.0.2 candidate: signed staging and gated promotion

v2.0.1 remains public stable Latest until v2.0.2 completes the signed staging gates and receives explicit promotion approval. The v2.0.0 and v2.0.1 tags, signed assets, and pinned updater trust remain unchanged. The v2.0.2 workflow stages an artifact only; this task stops at verified staging and does not publish stable Latest.

The supplied GitHub archive's root name and ZIP comment identify `rayhan138/watchman-c-@3b04d7d9446c6efa2a11d6b35aea019e5f7685a0`; the decoded ZIP SHA-256 is `bac1be3f7991de5785db66cc63569c0da123d075c1ab05bb57e85e10c6a11ab7`. `Build-Native.ps1` builds/tests x64 MSVC Release and runs CTest. On disposable GitHub Actions Windows runners it additionally runs the isolated non-admin startup-registration and actual desktop/runtime smoke suites; local builds skip these hosted-only checks. It then uses the locked Tauri CLI **bundle only** command on the prebuilt C++ executable. The base `src-tauri/tauri.conf.json` intentionally remains at 1.0.5 as historical frontend configuration; the native-only `src-tauri/native-package.json` overlays version 2.0.2 for packaging, and the build script enforces this split. `native-package.json` sets publisher `Noman Dhoni` and reuses the old per-machine NSIS uninstall key, shortcut behavior, running-process check, and `/P /UPDATE /R` restart-as-user contract. Tauri derives a second install-location key from the publisher, so `native-hooks.nsh` preserves a non-default v1.0.5/v2.0.0 path from the old `Software\blinkeye\Watchman` key when the new publisher key is absent, without changing the `Uninstall\Watchman` identity or making a second install. The NSIS hook restores `$INSTDIR` and its output path before copying files. The executable PE `CompanyName`, PE version, Settings badge, native updater version, installer DisplayVersion and staged feed are checked for consistency. The package skips WebView2 and replaces the v1 resource list. The install hook deletes known loose v1 probe files, not unknown user files. The pre-uninstall hook invokes ownership-checked startup cleanup for the current elevated user only; it never scans other profiles or removes user data, and cleanup errors do not block uninstall. The installer does not remove a shared Windows WebView2 runtime. Per-user registration and migration happen when that user launches the new app, not by scanning profiles from an elevated installer. The exact legacy Run command for the installed `watchman.exe` is recognized only with the supported `--minimized` (Tauri v1) or `--startup` (earlier native) argument; this includes Tauri v1's unquoted executable path with spaces. Other commands and same-named executables at different paths are preserved. A successful migration replaces the Run value with the native sign-in task.

## Data contract

* Source: `%APPDATA%\Watchman`. New active history: `%APPDATA%\Watchman.Native\watchman.db`. The legacy tree is not reused for writes. On first launch, after acquiring the instance guard, the app stages a full copy under a uniquely named sibling directory (rejects reparse points and locked data). It copies the DB plus sidecars from that snapshot to a **working** DB and integrity-checks it. A completed staging directory is renamed into place. `original-v1` inside it is the backup, not a live DB. Allow space for the snapshot **and** working database. Other Tauri identifier-specific app/WebView directories are untouched.
* **SQLite is the only history source**, including daily/per-app tables from earlier C++ builds. Copy the DB and its recovery files as a set. The app's normal schema upgrades are additive. If no DB or sidecars exist, start with an empty SQLite history. `history.json` and `history.json.bak` are copied as opaque backup files: neither is parsed, merged, changed, nor used for recovery. A corrupt DB, zero-length DB, or orphaned sidecars stop migration rather than substituting an empty DB. Incomplete `Watchman.Migrating-*` directories can be inspected offline.
* A completed native profile stays active. The migration does not remove any existing records, including records that a previous build may already have imported. An unmarked conflicting destination is left alone, not reset.
* Native settings are written to `HKCU\Software\Watchman`, without replacing existing native values. Registry writes are individually idempotent, not one cross-file/registry transaction. If interrupted, retry before manually editing imported registry values.

| v1 settings.json | Native setting |
|---|---|
| `startOnBoot`, `unitModeBits`, `hideGauges` | Autostart, UnitModeBits, HideHardwareGauges |
| `theme` = dark/light/system | Theme = 0/1/2 |
| `dataLimit`, `dataLimitEnabled` | DataLimitBytes (zero when disabled) |
| `widgetSettings.mode` = full/network-only/system-only | WidgetMode = 0/1/2 |
| `notifications.enabled`, `highUsageWarnings` | Combined alerts toggle |
| `notifications.warningSettings` | Traffic toggle/threshold and MB/GB unit, memory toggle/percent, CPU/GPU/disk/mainboard temperature toggles and thresholds |
| `memoryWarningEnabled`, `memoryWarningThreshold` | Fallback when nested memory settings absent |

Not translated: focus theme; other widget styling, order and individual visibility controls; speed-test results and server selection; period start; active profiles; connection/data/slow-network notifications and sounds; network-health, monitoring intervals, troubleshooter and export presets; unknown fields. They remain in the original JSON and snapshot. Native defaults apply where there is no equivalent or a scalar is outside its supported range. Legacy browser-side state is not imported. The native app's optional temperature backend differs from v1's bundled PowerShell/DLL probe.

## Update trust and staging

The full public key is identical in tags v1.0.1–v1.0.5. v1.0.5 is `2e490a181ce7eee09a38a13c65c375489b47a01c` (updater config blob `6f5f4b542b9e5f5681c6b7fe740b5c4f35bd2536`). Native Tools → Check for updates uses WinHTTP/TLS, a fixed production feed, bounded downloads, restricted HTTPS redirects, a strictly newer numeric version, and the exact x64 tag/asset URL. It prompts before download/install. The native verifier checks the **bytes and signed filename** with the pinned key; PE product version must also match. The executable is locked against writing/deletion through launch. There is no production command-line feed/key override. Run the updater unelevated; NSIS requests elevation. Verification is updater trust, **not Authenticode**. SmartScreen may still prompt. A successfully handed-off installer can remain under the user's temp directory.

`release-windows.yml` on this branch is **manual, artifact-only** (`contents: read`); it does not create releases or change the production feed. Only its signing step receives the existing signing secrets, not a PR job. `New-StagedFeed.ps1` verifies the signed installer before creating `latest.json` in a fresh staging directory. Three independent Windows runners test the exact staged artifact from v1.0.5, v2.0.0, and the current public v2.0.1 baseline. Publishing remains separately gated on all three passing. Keep the installer, `.sig`, feed and installed-executable hash from the **same successful run**; never substitute a rebuilt EXE for a signed one.

`Test-LegacyInstall.ps1` checks genuine v1 assets and a tampered copy. `Test-StableInstall.ps1` verifies and installs the immutable public v2.0.0 baseline; `Test-CurrentStableInstall.ps1` pins the public v2.0.1 asset hashes, verifies its signature, and installs it at a non-default path. Upgrade acceptance checks the original uninstall identity, publisher and PE `CompanyName`, custom path, restarted process, the seeded unquoted v1.0.5 `--minimized`/native `--startup` Run-command migration to one verified current-user task, settings, profile files, SQLite records, and current-user startup cleanup during uninstall. `Test-Staging.ps1` serves a **copy** of the manifest with only its URL changed over localhost HTTPS; version-specific isolated builds of the native updater check accepted and rejected responses and launch the signed candidate. No production DNS override, replacement signing trust, or production feed write is used. None of the released v1, v2.0.0, or v2.0.1 applications is redirected to staging.

## Recovery and limitations

1. Before rollout, snapshot the VM or independently back up the user's data while Watchman is stopped. Record install path, Run state, native settings if any and daily totals; cache and verify the v1.0.5 installer/signature.
2. On failure, stop Watchman, retain both data trees (including SQLite `-wal`/`-shm`) and any interrupted staging copy. Do not delete user data in the uninstaller. Uninstall v2, then reinstall the verified v1 binary at the original path. v1 should find its untouched original directory. If restoration is necessary, restore the **whole** quiescent directory from `original-v1` or the external backup. Never mix sidecars across snapshots. v2-only traffic after migration is not automatically merged back.
3. Launch v1 as the real user; check totals, settings, shortcuts and per-user startup. Before retrying v2 after rollback, archive the completed native profile and any imported native registry values if a fresh migration is needed. Do not overwrite newer data without comparing both histories. Revert the VM snapshot if recovery is uncertain.
4. Hosted Windows checks do not substitute for manual UAC with a different admin, multiple logged-on users, interactive cancel/restart, unusual ACLs or roaming profiles, interrupted power/disk writes, and real Win10/11 desktops. The uninstaller removes only startup registrations owned by the current elevated user's token; if a different administrator account supplies UAC credentials, another user's per-user Run value or sign-in task can remain. The installer does not scan profiles. Check for stale entries/tasks on shared machines. The inherited NSIS v1 fallback can force-stop a running process; unsaved in-memory samples cannot be recovered from a disk backup. Rollback to v1 is explicit, not an automatic feed downgrade.
